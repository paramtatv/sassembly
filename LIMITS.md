# Sassembly v1.1.0: verified limits

This page lists what a Sassembly v1.1.0 program can and cannot do. It is rewritten row by row for v1.1.0, and it keeps **only results that were verified**. Each claim was run on the four native targets (`x86_64-linux`, `aarch64-linux`, `aarch64-macos`, `x86_64-macos`) and under `yantra-run`. The release Stage 1 is `e0adbb0f…` (`sassembly-v1.1.0-stage1.elf`). Every probe image was built natively on each target, and the images were **byte-identical across all four**. The threads, files, randomness, memory and `YANTRA_RAM` rows were re-run with the release compiler and tools. The other rows were run with the previous v1.1.0 candidate compiler (`3476d012…`), which differs from the release compiler only in fork-join's region-purity checks. Every native result (exit status, halt line, stdout) was the same on all four targets. The only exception is a random draw, which differs by design.

**Columns.**
- **native**: the v1.1.0 native packages and `tools/t1-run.sh`, with no emulator.
- **yantra-run**: the RV64 emulator, Rust, in the v1.0.2 and v1.1.0-alpha archives.
- **verdict**:
  - **native**: passes natively on all four targets;
  - **emulator-only**: only `yantra-run` passes;
  - **not yet**: neither passes, or the claim was not verified for this page.

**How to verify.** Probes are the `.t1` files in [`examples/limits/`](examples/limits/). Two shorthands are used in the table:
- `nb P`: build natively, `tools/t1-build.sh --entry शृङ्खला स्वपरीक्षास्वप्रतिबिम्बम् -o P.elf examples/limits/P.t1`. From a package: `bin/sassembly-build --entry शृङ्खला स्वपरीक्षास्वप्रतिबिम्बम् -o P.elf examples/limits/P.t1`.
- `nr P`: run natively with no fallback, `T1_RUN_REQUIRE_NATIVE=1 tools/t1-run.sh P.elf`. From a package: `bin/sassembly-run P.elf`.

With `T1_RUN_REQUIRE_NATIVE=1`, anything the native runtime cannot do is a refusal, never a silent emulator run. The yantra side is `examples/limits/run.sh P [yantra-run options] [-- args]`, with `STAGE1` set to the v1.1.0 Stage 1.

**Two kinds of refusal.**
- "refused (flag)": a `yantra-run` flag, which the native route refuses.
- "refused (rerun)": an instruction or device the translator does not lower; `t1-run.sh` would rerun the program under `yantra-run`.

**What was verified from a package.** The table was verified with `tools/t1-build.sh` and `tools/t1-run.sh`. Those use the same Stage 1 and translator as the packages. The file grant (`YANTRA_FILES`) and the float self-check were also run from the `x86_64-macos` package, with the same results.

**Not re-run for this page:**
- the `cargo test` commands of earlier versions of this page, because the Rust is unchanged since v1.1.0-alpha;
- QEMU;
- `yantra-wasm`.

## Notes
- **The four native targets never disagreed.** Windows has no native target yet. The Rust `yantra-run` from the v1.0.2 archives runs there.
- **Threads are emulator-only, and are refused by name natively.** `tools/t1-run.sh` reruns a threaded image under `yantra-run`; a native package refuses it.
- **File grants.** Natively, use `tools/t1-run.sh --files DIR` or `YANTRA_FILES=DIR`. A package's `bin/sassembly-run` takes `YANTRA_FILES=DIR`.
- The idle timeout (30 s) and the 64 MiB session cap of the loopback socket are cited from [NETWORKING.md](NETWORKING.md) only.
